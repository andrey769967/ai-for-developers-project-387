# TypeSpec — источник контракта, сервер написан вручную

`contract/main.tsp` — единственный источник истины для API: из него генерируются OpenAPI, типы клиента (`web/src/lib/api/schema.d.ts`) и модели API сервера (`server/src/api-schema.d.ts`). `server/src/types.ts` — тонкие алиасы на сгенерированные модели плюс ручной класс `ApiError`. Маршруты и логика Fastify написаны руками: эмиттера TypeSpec для Fastify не существует. Соответствие моделей контракту держится на генерации (расхождение ломает `tsc`), соответствие поведения — на тестах.

## Consequences

- Порядок сборки обязателен: контракт → OpenAPI → сгенерированные типы → сервер. Корневой `npm run build` выполняет его целиком; сборка сервера без перегенерации типов возможна, но увидит старый снимок контракта.
- `server/src/api-schema.d.ts` лежит в git, как и клиентские типы: снимок виден в диффе, а сборка не требует запущенного генератора.
- Изменение моделей в контракте без правки сервера падает на `tsc`: добавленное обязательное поле, удалённое или переименованное поле, смена типа ломают код, который эти модели конструирует или читает. Маршруты и тела ответов при этом по-прежнему не привязаны к `operations[...]`: смена кодов ответов или появление нового маршрута проверяется только тестами.
- Поведение по-прежнему не генерируется: новый маршрут в контракте требует ручного обработчика и теста, иначе он просто не существует в сервере.
- Сгенерированные типы описывают только объявленное в контракте, поэтому неполный контракт напрямую ослабляет типизацию и фронтенда, и сервера.
